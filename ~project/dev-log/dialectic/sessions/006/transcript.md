# Model

**DDL** (Data Definition Language) — statements that change the *structure* of the database. `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE`. These define what can exist.

**DML** (Data Manipulation Language) — statements that work with *data inside* existing structures. `INSERT`, `UPDATE`, `DELETE`, `SELECT`. These operate on rows within already-defined tables.

The practical tension: DDL operations are heavier, sometimes require elevated permissions, and can fail in ways DML doesn't. More importantly, they're harder to undo and harder to query — you can't easily ask "show me all tag types" if each tag type *is* a table, because tables aren't rows.

In SurrealDB specifically, `DEFINE TABLE author TYPE RELATION` would make the database structurally aware of `author` as a relation type — which is clean and enables efficient graph queries. But every time a user creates a new tag type, you're altering the schema, not inserting a record.

The alternative — one `edges` table with a `type: "author"` field — keeps everything as DML. Tag types are just string values on records. Queryable, listable, deletable like any other data. Less efficient for graph traversal, but the schema never changes after initial setup.

The reason this matters for your model specifically: if tag types are navigable entities (which your model implies — you should be able to click "author" and see all authors), they need to be *rows*, not *tables*. A table isn't something you can pin, annotate, or navigate to. A row is.

# Model

The gap in both options is the same: edge type as stored data (table name or string) and edge type as navigable Object are two things kept in sync by convention.

One way to close it structurally: make the edge `type` field a **record reference**, not a string.

```
edges record:
  in:   objects:book1
  out:  objects:hemingway
  type: objects:author     ← a record link, not a label string
```

Creating a tag type = inserting a record into `objects`. Nothing else.

SurrealDB supports filtered graph traversal, so you don't fully lose the `->` syntax:
```
SELECT ->edges[WHERE type = objects:author]->objects FROM objects:book1
```

Slower than named tables, but the model is structurally unified.

# Model

In SurrealDB, an edge is a record created with `RELATE`:

```sql
RELATE book:1->author->hemingway:1
```

This creates a record in the `author` table that looks like:

```json
{
  "id": "author:⟨ulid⟩",
  "in": "book:1",
  "out": "hemingway:1"
}
```

You can add arbitrary fields:

```sql
RELATE book:1->author->hemingway:1 SET confidence = 0.9
```

And traverse it:

```sql
SELECT ->author->objects.* FROM book:1
-- or in reverse:
SELECT <-author<-objects.* FROM hemingway:1
```

The edge record lives in the `author` table. `in` and `out` are built-in fields — record links back to the source and target nodes. The table name (`author`) is what gives the edge its semantic meaning in this model.

That's the native SurrealDB shape. In the unified model we were discussing, you'd instead do:

```sql
RELATE book:1->edges->hemingway:1 SET type = objects:author
```

Same structure — `in`, `out`, plus a `type` field that's a record link rather than being encoded in the table name. The edge record would be in the generic `edges` table, and `type` carries what the table name would have in the native approach.

# Model

Three tables.

**Nodes** are things — files, URLs, groups, people, concepts, devices. Anything that exists independently and can be related to other things.

**Edge types** are the names of relationships — "author", "genre", "contains". They describe what a connection means, but aren't things themselves.

**Edges** are the connections — they link one node to another and carry an edge type that says what the relationship is.

A book and Hemingway are both nodes. "Author" is an edge type. The edge between them says: this book is connected to Hemingway, in the way of authorship.

Hemingway can also be connected to a person node, a Nobel Prize node, a Cuba node — each edge naming a different kind of relationship. Navigation works in any direction: from the book to Hemingway, from Hemingway to all his books, from "author" to every authorship relationship in the system.

# Model

**0.5** had nine tables that reflected how the application was built over time — each new concept got its own table.

Files and spaces lived in `objects`. Tag values like "Hemingway" lived in `tag_definitions`. The categories those values belonged to — "author", "genre" — lived in `tag_types`. Devices got their own table. Then five separate edge tables handled different kinds of relationships: `tagged`, `typed`, `contains`, `excludes`, `sourced_from`.

To say "this book was written by Hemingway" required two hops: one edge from the book to the Hemingway record, and a second edge from the Hemingway record to the "author" type. The relationship and its meaning were stored separately.

Nothing was truly navigable from any direction. Hemingway existed in `tag_definitions`, not `objects` — you couldn't arrive at him the same way you'd arrive at a file or a space.

---

**0.6** has three tables that reflect how information actually works.

Hemingway and the book are both nodes. "Author" is an edge type. One edge connects them and names the relationship directly. Navigation works symmetrically in both directions. Any node — a book, a person, a concept like "Science Fiction" — can be arrived at, explored, and related to other things in the same way.

The reduction from nine tables to three isn't just simpler infrastructure. It's the model catching up to the concept.
