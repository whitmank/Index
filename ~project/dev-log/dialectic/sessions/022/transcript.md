**What the Album case actually introduces**

The current model has one relationship type: tag membership. Tags classify objects — "this file is `genre:jazz`." But Album → Song is a different kind of relationship: *composition*. The song is *part of* the album, not merely classified by it.

**The unified picture**

An object now has two ways to define its membership:

```

children: [id, id, id, ...]                                    // explicit, ordered
```

Either, both, or neither. A plain file has neither. An album has `children`. A music library space has a `query`. A curated playlist might have both — pull in anything tagged `playlist:road-trip` *and* some manually pinned tracks in a specific order.

**The hierarchy**

```
Music Library  →  [Album A, Album B, ...]      (query or explicit)
Album A        →  [Song 1, Song 2, Song 3]     (explicit, ordered)
Song 1         →  (leaf — no children)
```

This is a graph with containment edges. The existing tag edges remain for classification. Now there are two edge types: *tagged-with* and *contains*.

Graph view becomes meaningful here — you can render the Album → Song hierarchy spatially, which you can't do today.

Currently, "adding an object to a space" assigns tags (`query.all` tags get written to the object). That write semantic works for classification-based spaces.

So the write semantic has to fork:
- Query-defined container → assign tags to the incoming object
- Children-defined container → append to `children` array

# Model

Implied by `children` — but with a cost.

If only `children` exists, finding an object's parent requires a reverse lookup: scan all objects whose `children` array contains this ID. That's a graph traversal query, not a direct property read. In SurrealDB that's expressible but it's a full table scan unless indexed.

# Model

Yes. This is exactly what SurrealDB edges are for.

Instead of two arrays to keep synchronized:

```sql
RELATE object:album -> contains -> object:song1 SET order = 1;
RELATE object:album -> contains -> object:song2 SET order = 2;
```

Traversal in both directions is native:

```sql
SELECT ->contains->object FROM object:album;   -- children
SELECT <-contains<-object FROM object:song1;   -- parents
```

The sync problem disappears — there's one source of truth (the edge record), not two arrays pointing at each other. And the edge itself is a record, so it carries properties: `order` for track position, or anything else describing the relationship.

This also cleanly separates the two containment mechanisms:

- `query` property on the object → dynamic membership (no edges, derived at read time)
- `contains` edges → explicit membership (stored, ordered, traversable)

The data model then becomes:

```
objects table     — all nodes (files, URLs, albums, spaces, everything)
contains edges    — explicit parent-child relationships with order
tags              — classification (existing)
```

Three primitives. Clean.

The one thing to think through: when both `query` and `contains` edges are present on a container, resolving membership means union-ing two sources — edge traversal and query evaluation. That's the rule you'll need to pin down, but it's application logic, not a model problem.
