# Development Log — 2026-03-26 to 2026-04-03

## Sessions 011–015: Infrastructure Repair, Finder Import, and Type System Redesign

Sessions 011–015 span two distinct arcs. The first (011–013) was infrastructure repair
and UI polish: settings restructure, appearance persistence, tag dedup semantics, detail
pane refinements. The second (014–015) was major feature work: a full Finder integration
via a macOS Finder Sync Extension, and a fundamental redesign of the type system around
an object schema model.

## Session 011 — Settings Restructure and Appearance Persistence

### Devices Tab

The Settings "General" tab was replaced entirely with a device list. This followed
naturally from session 010, which built the `devices` table as a first-class record
system. The "General" label no longer described anything specific — the tab had become
a thin wrapper around a device entry and an About section. Both were removed.

The new "Devices" tab shows all device records from the Zustand store. The current
device is marked with a `this device` badge matched via `deviceOrigin`. Creating the tab
as a live list rather than a static display means new devices appear automatically as
they're added (future sync path).

### Appearance Persistence Regression

Appearance settings (background color, opacity) were not surviving app relaunch. Root
cause: Chromium's localStorage LevelDB writes are asynchronous to disk. When the
Electron renderer process is killed before the flush, the write is lost. This is a
known Electron pattern — process lifecycle doesn't guarantee localStorage durability.

The fix follows the existing `window-settings.json` pattern: appearance settings are
now written to `~/.index/appearance.json` by the main process, over IPC. `initAppearance()`
in the renderer is async and awaited in `main.jsx` before React renders. localStorage
is retained as an in-session cache and seeded from the file on load.

A preload-based approach was attempted first (`require('fs')` in preload) and failed.
Electron v20+ sandboxes renderers; preload `require` is limited to `electron`, `events`,
`timers`, `url`. The attempt crashed the preload, producing a transparent window.
IPC-to-main is the correct pattern for anything requiring filesystem access.

A safety guard was added: `bgA <= 0` in `loadFromStorage()` resets opacity to the
default (0.75). An opacity of zero makes the app invisible and unrecoverable without
keyboard access.

### Case-Insensitive Tag Deduplication

The user observed that creating "Artist" and "artist" as separate tags was possible
when it shouldn't be. The decision: preserve the user's casing on write, but treat
names as equal regardless of case for deduplication and lookup.

Implementation: `string::lowercase(name) = string::lowercase(input)` in SurrealDB
`createTag`, `createTagType`, `updateTag`, and `findOrCreateSystemTag`. No normalization
of stored values — "My Book" writes as "My Book", but attempting to create "my book"
finds the existing record instead. This pattern is applied consistently across all tag
creation paths.

## Session 012 — Detail Pane Polish

### Tag Creation Bug

Tag creation was failing in some cases without user feedback. Root cause: `string::lowercase(NULL)`
throws in SurrealDB when a `tag_definitions` record has a null name field. Fixed with
`IS NOT NONE AND IS NOT NULL` guards before the `string::lowercase()` call.

Additionally, tag name deduplication was made type-scoped. Previously, "author" as
a user tag would conflict with "author" as a field tag type. Same name under different
tag types now coexists cleanly.

### KindField in Detail Pane

The KIND system tag was promoted to a first-class field in `ObjectDetailPane`. The
`KindField` component renders in the `sharedInfo` block — above the ADDED date row,
in a consistent badge+edit pattern with the rest of the tag system. KIND is filtered
out of the Tags section below to prevent duplication.

This put the object's type front and center without introducing a new UI pattern.
(This component would later be renamed `TypeField` in session 015.)

### Source Add Affordance

The `+` Add source card below the sources list was replaced with an inline SVG
circle-plus icon adjacent to the SOURCES section header. The icon is a proper SVG
(circle stroke with crosshair), not a text character. `viewBox="0 0 16 16"` with 1px
padding prevents stroke clipping. `currentColor` means hover still works.

### Nav State Persistence

Manual app refresh was losing the user's location in the application. Fixed by
persisting the full nav state to localStorage: `activeTopLevelView`, `activeSpaceId`,
`activeView`, `detailObjectId`. On mount after `loadAll()` completes, the state is
restored via `enterSpace` and local state updates.

### Typography Exploration

The global font was explored during this session. Spectral (a Production Type serif
designed for dense screen text) was downloaded from Google Fonts, bundled locally
(Electron CSP blocks external stylesheet links), and loaded with weights 300, 400,
500-italic, and 600-italic. Space rows were styled bold + italic (weight 500).
Spectral was shelved in favor of Arial for simplicity. Files are retained in
`src/fonts/` for future use.

## Session 014 — Finder Import Flow

Session 014 was a full-session build of the most complex native integration in the
application to date: a macOS Finder Sync Extension that brings Index into the Finder
context menu.

### Architecture

**FinderSyncExtension** — A Swift `.appex` built with `FIFinderSyncController`. When
the user right-clicks any folder or file in Finder, "Add to Index" appears as a
top-level context menu item. The extension uses `NSWorkspace.open` to fire
`index://import?path=...` as a URL event.

**`IndexSync.app`** — A minimal host app wrapping the `.appex`. Finder Sync extensions
must be embedded in a real app bundle to be registered by `pkd`. The host has no UI —
it exists only to provide a container.

**`index://` URL scheme** — Electron registers this scheme via `protocol.handle`. The
`app.on('open-url', ...)` handler receives the URL, extracts the path, and emits
`main:importFolder` to the renderer.

**`fs:readFolder`** — A new IPC handler in `electron/main/ipc/fs-handlers.js`. Reads
a folder tree recursively, returning items with `path`, `name`, `type`, and `relativePath`.
Directories appear before their contents. Dotfiles and system directories are skipped.

**`ImportModal`** — The renderer presents the folder tree as a per-folder tag entry
UI. Features: batch tag application per folder, already-indexed detection (objects
with matching URIs are marked), space creation (either a static `contains` space or
a rule-based space).

**`build-host.sh`** — Build + sign script for repeatable development iteration. Key
finding: `codesign --deep` re-signs the embedded extension and strips its entitlements.
The script signs the host and the extension binary separately.

### Obstacles

This was the first session with significant native toolchain friction. Four distinct
obstacles were hit and resolved:

- **`@objc(FinderSyncExtension)` broken Info.plist lookup** — Swift's `@objc` attribute
  prepends a module prefix that doesn't match the bare class name in Info.plist. Removed
  the attribute; use the bare Swift class name.
- **`NSHomeDirectory()` sandbox** — In a sandboxed extension, `NSHomeDirectory()` returns
  the app container path, not the real home directory. Switched to `URL(fileURLWithPath: "/")`
  as `directoryURLs` to allow menu display for any path.
- **`--deep` strips extension entitlements** — `codesign --deep` re-signs embedded
  components, stripping each component's own entitlement set. Sign the host app and the
  `.appex` binary separately.
- **Ad-hoc signing rejected** — `pkd` (the system extension daemon) rejects ad-hoc signed
  extensions. A free Apple Developer account certificate is required.

## Session 015 — Type System Redesign

Session 015 opened with a conceptual question and became the most architecturally
significant session since 006. The outcome: a complete redesign of how object types
work, implemented end-to-end in a single session.

### The Question

The user had been thinking about `kind` as a privileged tag type that defines the
schema of an object: a book has an author and ISBN; a song has BPM and key. The current
model treated `kind` as any other tag — structurally flat, late-bound, mutable. The
observation: type should govern what metadata fields an object displays and what the
capture handler targets.

### The Contradiction

**Current:** `kind` is a tag; all objects have the same flat schema; type is a label applied after the fact.

**Proposed:** `kind` (or type) is a schema selector; it governs display fields and possibly capture behavior; changing it reshapes the visible fields.

The tension: if type is a tag, it's user-defined and mutable. If type is a schema
declaration, it has structural weight. These are different things.

### The Synthesis

The resolution: **type is a tag, but a tag definition can carry a UI schema**. The object stays flat. The schema is an interface concern, not a data constraint.

Concretely:
- A Type definition (e.g. "book") is a tag definition under tag type `type`
- That record carries a `schema` field — an ordered list of tag type IDs
- The detail pane reads the object's Type tag, fetches the schema, renders those fields
- The object can have any tags; the schema just guides the default path

The further synthesis: **tag types are the field system**. Schema fields are not a new
data structure — they are tag types (`author`, `published`, `isbn`). A book schema is
`[tag_types:author, tag_types:published, ...]`. The same `author` tag type is reusable
across schemas. No new tables. No new concepts. The existing type system was already the
field system.

### Terminology

`kind` was dropped entirely. The relationship is:
```
object  ==type=>  'book'
object  ==type=>  'song'
```

"Object Type" (user-facing, often just "Type") and "Tag Type" (system-facing) are
distinct qualified terms. The tag type formerly named `kind` is renamed `type` at all
layers: registry, migration, services, UI.

### Implementation

**`kind` → `type` rename (all layers):**
- `domain/tag-types.js` — key, label, description
- `db/connection.js` — migration step: repoint `typed` edges from `tag_types:kind` to
  `tag_types:type`, delete old record (idempotent, safe for existing data)
- `db/services/object-service.js` — `findOrCreateSystemTag` call
- `ObjectDetailPane.jsx` — `KindField` → `TypeField`, `kindTag` → `typeTag`, label
- `TagAssignmentSection.jsx` — exclusion filter

**Schema field seeding (`seedTypeSchemas()` in `connection.js`):**
- Ensures field tag types exist (`author`, `published`, `genre`, `isbn`, `artist`,
  `director`, `format`, `pages`, `year`) with `display: false`
- Writes standard schemas onto type tag_definition records for book, document, image,
  video, audio on every boot
- Uses `name ?? ''` coalesce in SurrealDB query to handle null-name records safely

**`TypeSchemaSection` (new component):**
- Renders a "Details" section in `ObjectDetailPane` with one row per schema field
- Empty slots are clickable to add; populated slots show the existing tag badge (editable,
  removable)
- Uses the same `createTag` + `assignTag`/`unassignTag` store actions as the rest of the
  tag system
- Mounts between the info block and Sources when the object has a type with a schema

**`TagAssignmentSection` store fragmentation fix:**
- The component had been maintaining its own local `assignedTags` state via direct IPC,
  bypassing the store entirely
- After a tag mutation, only its local state updated; `store.objectTags` was never
  refreshed; `typeTag` in `ObjectDetailPane` went stale; the Details section collapsed
- Fixed: component now reads from `store.objectTags[objectId]` and calls `loadTagsForObject`
  on mutation — same source as every other component

**Tags section schema exclusion:**
- `TagAssignmentSection` accepts `excludeTypeIds` prop
- `ObjectDetailPane` passes `typeTag.schema` as `excludeTypeIds`
- Tags shown in Details (schema fields) are excluded from the Tags section

**TagsView restructure:**
- Types pinned as first-row nav item, labeled "Types", selected by default
- Remaining tag types grouped under "Tag Types" divider
- Tag count numbers removed from nav rows
- Schema editor panel added for type values: shows ordered field list, Add field input
  creates new tag types if the name doesn't exist
