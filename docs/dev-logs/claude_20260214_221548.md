## Key Decisions

**SurrealDB Ephemeral Storage**: Database runs in temporary directory with fresh state on each launch. Data persists to `~/.index/` JSON files on disk, hydrated on startup. This pattern ensures data integrity and simplifies backup/versioning while providing fast in-memory query performance.

**Content Hash Recovery**: Implemented SHA-256 file hashing to track files by content rather than path. When source files are moved or renamed, system automatically searches parent directories to recover correct paths. This resilience is critical for long-term file reference stability.

**Glassmorphic Overlay Architecture**: Window created as frameless, transparent overlay with native blur effects (macOS vibrancy). Positioned at 15% from top of screen, hidden by default, toggled via global hotkey (Cmd+` / Ctrl+`). This matches the product vision of an ambient, non-intrusive interface.

**IPC Security Model**: Strict context isolation with preload script acting as security boundary. Only essential APIs exposed to renderer. Database operations sanitized in main process before execution.

**File Watcher with Debouncing**: 500ms debounce on file system events prevents excessive reloads during rapid changes (e.g., batch edits). Watcher broadcasts changes to renderer, triggering automatic UI refresh without user intervention.

**Platform-Aware Shortcuts**: Keyboard shortcuts detect platform (macOS vs Windows/Linux) and use appropriate modifier keys (metaKey vs ctrlKey). This ensures native feel across operating systems.

**Separation of Concerns**: Database logic isolated in `db/` directory, IPC handlers in `ipc/`, utilities in `utils/`, watchers in `watchers/`. Each module has single responsibility with clear API boundaries.

## Technical Notes

### SurrealDB Integration
- Binary spawned as child process with stdio piping for readiness detection
- Connection via WebSocket protocol (`ws://127.0.0.1:8000`)
- Database credentials: root/root (dev credentials, secured in production)
- Namespace: `index`, Database: `main`
- Tables: `objects`, `relationships`, `tags` (schemaless)
- Startup sequence: spawn → connect → signin → use namespace → init tables → hydrate
- Shutdown sequence: persist → close connection → SIGTERM → cleanup temp dir

### Data Persistence Format
Directory structure at `~/.index/`:
```
.index/
├── objects/
│   └── {name}_{id}.json     # One file per object
├── relationships/
│   └── relationships.json   # Single file (array)
└── tags/
    └── tags.json           # Single file (array)
```

Objects stored individually for easier external editing and version control. Relationships and tags stored as single arrays (simpler for Phase 0, may split in future phases).

### File Recovery Algorithm
1. Check if file exists at original path
2. If not, calculate SHA-256 hash from `source_metadata.content_hash`
3. Search original directory (2 levels deep, excludes hidden files)
4. If not found, search parent directory (2 levels deep)
5. Return most recently modified match
6. Update object source path if recovered, mark as missing if not

Recovery runs on hydration and on-demand. Maximum depth of 2 prevents performance issues on large filesystems.

### IPC API Surface
```javascript
window.electronAPI = {
  db: {
    query(sql)                    // SELECT queries
    mutate(sql)                   // INSERT/UPDATE/DELETE (auto-persist)
    getAll(table)                 // Bulk load
    createObject(data)            // Create with metadata derivation
    updateObject(id, data)        // Update with metadata refresh
    createRelationship(data)
    createTag(data)
  },
  fs: {
    pickFile()                    // Native file picker
    getPathForFile(file)          // Convert File to absolute path
  },
  openSource(source)              // Open file or URL
  onObjectsChanged(callback)      // Listen for file changes
}
```
