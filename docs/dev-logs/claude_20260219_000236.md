## Key Decisions

- **`tags` → `tag_definitions`, `object_tags` → `tag_assignments`**: Better naming that clarifies intent — definitions are the schema, assignments are the join records
- **`source` split into `source_local` + `source_remote`**: High-cardinality path data belongs on the object, not in tags; the split makes dual-source objects (local + remote mirror) a first-class case
- **System tags find-or-create, not pre-seeded**: System tag records are created on first use rather than pre-populated, keeping the database lean and avoiding orphan records
- **System tag editing creates new + unassigns old**: Rather than mutating the shared tag definition (which could affect other objects), editing a system tag on an object creates a corrected definition and re-points the assignment — preserving shared definitions correctly
- **Consistent system tag order via constant**: `SYSTEM_TAG_ORDER` array in `TagAssignmentSection.jsx` ensures `media_type` always renders above `file_extension` regardless of DB query order
- **Removed relationships table**: Simplifying to tags-only model for now; relationship graph is deferred
- **`extractMediaType` uses extension-first, MIME-type fallback**: Extensions are more reliably available (especially for local files) so they take precedence; MIME type provides a catch-all for edge cases

## Blockers / Open Questions

- **Data migration for existing installs**: Any `~/.index/` directory created before this session uses `tags/` + `object_tags.json`. The new hydration layer will not find those files. A one-time migration step (rename dirs + file) must be written before shipping this branch to users with existing data
- **Duplicate system tag definitions**: The inline edit flow calls `createTag` without checking if a definition with the target `(type, name)` already exists. Under the DATA_MODEL spec, `(type, name)` should be unique for system tags. Either the IPC `db:createTag` handler needs a find-or-create path, or the component must query first

## Technical Notes

- SurrealDB tables are SCHEMALESS — uniqueness constraints described in DATA_MODEL.md are enforced in application layer only (not at DB level)
- `tag_assignments` is persisted as a single flat JSON file (`~/.index/tag_assignments.json`); all other tables use one-file-per-record in subdirectories
- The `objectId` passed through IPC handlers is a plain string ID (without table prefix); full SurrealDB record IDs are assembled in the handler as `objects:{id}`, `tag_definitions:{id}`, etc.
- System tag assignment happens synchronously within `db:createObject` before the final `persistToIndex` call — all three writes (object, system tags, assignments) flush in one persistence cycle
- `getMimeType()` in `metadata.js` is a lighter private function used only for `deriveSourceMetadata()`; the public `extractMediaType()` uses its own extension switch with `getMimeType` as a fallback — the two are intentionally decoupled
