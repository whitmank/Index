## Key Decisions

### Tag ID Normalization Strategy
**Decision:** Normalize all tag IDs to plain strings (without `tags:` prefix) throughout the application stack.

**Rationale:** SurrealDB returns RecordId objects in format `{ id: "tags:abc123" }` which caused mismatches during query evaluation. By normalizing to plain strings everywhere (frontend stores, IPC handlers, query evaluation), we ensure consistent comparisons.

**Implementation:** Created `extractPlainId()` helper in IPC handlers and `normalizeTagId()` in query evaluation to handle both RecordId objects and string formats.

### Query Evaluation Location
**Decision:** Implement query evaluation in backend (IPC handler) rather than frontend.

**Rationale:**
- Backend has direct access to all objects and object_tags without additional IPC round trips
- Reduces frontend complexity and bundle size
- Enables future optimizations like query caching or database-level filtering
- Single source of truth for query logic

### System "ALL" Collection
**Decision:** Create virtual system collection `__system_all` that appears first in the list.

**Rationale:** Provides clear UX for "show all objects" state. Users can click "ALL" to deactivate any active collection filter, making the filter state explicit rather than implicit.

### Optimistic Updates
**Decision:** Update frontend collections state immediately after successful database mutations.

**Rationale:** Provides instant UI feedback without requiring full reload. Collections are small datasets where optimistic updates are safe.

## Critical Bugs Found and Fixed

### Bug 1: Tag ID Format Mismatch
**Symptom:** Collections returning zero objects even when objects had matching tags.

**Root Cause:** SurrealDB returns tag IDs as RecordId objects `{ id: "tags:abc123" }` in some queries but plain strings `"abc123"` in others. Query evaluation was comparing `{ id: "tags:abc123" }` against `"abc123"`, which always failed.

**Fix:** Implemented `normalizeTagId()` function in `db:evaluateCollection` handler to extract plain ID from both formats before comparison. Also normalized query arrays during collection creation/update.

**Location:** `electron/main/ipc/db-handlers.js` lines 711-719, 513-521, 604-612

### Bug 2: SurrealDB Double-Array Wrapping
**Symptom:** `collection is undefined` errors when trying to access collection properties.

**Root Cause:** SurrealDB wraps single-record query results in nested arrays: `[[{record}]]`. Standard unwrapping only handled one level.

**Fix:** Added second level of array unwrapping in `db:evaluateCollection`:
```javascript
if (Array.isArray(collection) && collection.length > 0) {
  collection = collection[0];
}
if (Array.isArray(collection) && collection.length > 0) {
  collection = collection[0];  // Second unwrap
}
```

**Location:** `electron/main/ipc/db-handlers.js` lines 696-702

### Bug 3: Query Field Corruption During Persistence
**Symptom:** Collections created with valid queries would return all objects on evaluation.

**Root Cause:** Tag IDs in query arrays were being stored as RecordId objects instead of plain strings. When loaded back, normalization failed because the structure was already corrupted at storage time.

**Fix:** Added `extractPlainId()` mapping during collection creation and update to ensure only plain string IDs are persisted:
```javascript
query: {
  all: (query.all || []).map(extractPlainId),
  any: (query.any || []).map(extractPlainId),
  none: (query.none || []).map(extractPlainId),
}
```

**Location:** `electron/main/ipc/db-handlers.js` lines 527-531, 620-624

### Bug 4: Frontend ID Extraction Inconsistency
**Symptom:** Collections sidebar sometimes showed duplicate items or failed to activate collections.

**Root Cause:** Some parts of frontend code extracted ID as `id.id.split(':')[1]` while others used `id.split(':')[1]`, causing mismatches when ID was already a plain string.

**Fix:** Standardized ID normalization in collections store to handle both cases:
```javascript
if (typeof id === 'object' && id.id) {
  id = id.id;
} else if (typeof id === 'string' && id.includes(':')) {
  id = id.split(':')[1];
}
```

**Location:** `src/store/collections.js` lines 34-38, 73-78

## Technical Notes

### SurrealDB Query Result Unwrapping
SurrealDB's result format varies by query type:
- `SELECT * FROM table` returns `[array]` (single unwrap)
- `SELECT * FROM table:id` returns `[[record]]` (double unwrap)
- Always check array depth before accessing records

### ID Formats Across Stack
Three ID formats encountered:
1. RecordId object: `{ tb: "tags", id: { String: "abc123" } }` or `{ id: "tags:abc123" }`
2. Prefixed string: `"tags:abc123"`
3. Plain string: `"abc123"`

Always normalize to plain string for comparisons. Use prefixed string only for database queries.

### Zustand Store Patterns
Collections store follows these patterns:
- `loading` flag for async operations
- `error` for user-facing error messages
- Optimistic updates with rollback on failure (not implemented yet)
- Getter functions (`getAllCollections()`) for derived state

### File Watcher Integration
Collections automatically persist to `~/.index/collections.json` after every mutation. The existing file watcher in `electron/main/watchers/objects.js` doesn't watch this file, so changes from external edits won't trigger reloads. Consider adding watcher if manual JSON editing becomes a workflow.

### CSS Architecture
CollectionsSidebar.css uses BEM-like naming:
- `.collections-sidebar` - Root container
- `.collection-item` - Individual collection row
- `.collection-editor-overlay` - Modal backdrop
- All interactive elements use descriptive class names for maintainability

## Notes on Debugging Process

The debugging session revealed systematic ID normalization issues across the entire stack. The root cause was SurrealDB's inconsistent ID format in different query contexts. The fix required:

1. Understanding SurrealDB's RecordId type structure
2. Tracing ID flow from database → IPC → frontend → comparison
3. Adding normalization at every boundary (persistence, retrieval, display, comparison)
4. Extensive console logging to verify normalization at each step

Key lesson: When working with ORMs or database libraries, always establish clear ID format contracts at architectural boundaries.
