# Model

**Conceptual** — Index is a semantic layer over the filesystem: meaning over location. Objects exist in multiple contexts via tags and containers. Containers are objects with `container: true`; membership is `(query ∪ contains_edges) − excludes_edges`. The active container is the capture target.

**Technical** — Persistent SurrealDB at `~/.index/surreal/`. Four edge tables. Two system containers (`objects:root`, `objects:all`). Single Zustand store. LIVE SELECT on seven tables. `evaluateContainer` resolves membership server-side. Three top-level views; CMD+K / CMD+L separated. Tag types are first-class `tag_types` records connected via `typed` edges.

**Synthesis** — Unified object/container model is complete through all layers. Tag type system with `typed` edges is settled. Root pinning via `contains` edges from `objects:root` is the canonical mechanism. System is bootable; core navigation, reactivity, and capture are functional.

**Key Decisions**
- Container = `object { container: true }`, no separate table
- Pinning = `contains` edge from `objects:root`, no boolean field
- `evaluateContainer` is server-side, called on load and live events
- Tag type = `tag_types` record + `typed` edge (not a string field)
- CMD+K = command interface; CMD+L = space navigator

**Open**
- `objects:all` not appearing at root — `evaluateContainer('objects:root')` returns empty; cause unidentified
- Descriptions not showing until restart — `description` backfills on next boot; no in-flight mechanism
- `display: false` system tags leak into CreateSpaceModal tag pool
- Graph edge rendering not built
- Object detail view not built (`onObjectOpen` stubbed)
- No UI affordance for manually pinning objects to a container (`addContains`)

## Edges as first-class primitives

The old model used **join tables with foreign key fields** — regular schemaless records that happened to store two IDs:

```js
// tag_assignments (old)
{ id: "tag_assignments:xyz", object_id: "objects:abc", tag_id: "tag_definitions:def" }
```

The new model uses **SurrealDB `RELATE` edges** — a distinct record kind with a direction, defined as `TYPE RELATION`:

```sql
DEFINE TABLE tagged SCHEMALESS TYPE RELATION;
RELATE objects:abc->tagged->tag_definitions:def
```

This is not cosmetic. The differences that matter for documentation:

**Edge records have `in` and `out` instead of named foreign key fields.** The normalized form arriving at the renderer is `{ id, in, out }` where `in` and `out` are plain strings. `normalizeRecord` was explicitly extended to stringify these fields — prior to that fix, `in`/`out` arrived as opaque SurrealDB `RecordId` objects and comparisons silently failed.

**Direction is semantic.** `object→tagged→tag_definition` means "this object has this tag." `tag_definition→typed→tag_type` means "this tag belongs to this type." `container→contains→object` means "this container explicitly includes this object." The arrow is part of the model, not an implementation detail.

**Edges can carry data.** The `contains` edge has an `order` field — explicit ordering of a container's contents is expressed as edge metadata, not as a field on either endpoint. This is only possible because edges are records.

**Query patterns change accordingly:**
```sql
-- Old: join table scan
SELECT * FROM tag_assignments WHERE object_id = objects:abc

-- New: edge traversal
SELECT out FROM tagged WHERE in = objects:abc
```

**LIVE SELECT works on edge tables.** `onTaggedLive`, `onContainsLive`, `onExcludesLive`, `onTypedLive` all subscribe to edge table changes directly. The store reacts to individual edge CREATE/DELETE events without rescanning.

**Five edge tables are now in use:**

| Table | Type | Carries |
|---|---|---|
| `tagged` | `objects → tag_definitions` | — |
| `contains` | `objects → objects` | `order` |
| `excludes` | `objects → objects` | — |
| `typed` | `tag_definitions → tag_types` | — |

The `typed` edge in particular replaces what was a `type: string` field on `tag_definitions` — the string could name a type but couldn't *reference* one. An edge can. This is what makes tag types first-class records rather than just labels.

---

This needs its own section in GLOSSARY.md — not just a footnote under Tag or Container. It's the architectural pattern that underpins how all relationships work now.
