# Model

**DDL** (Data Definition Language) — statements that change the *structure* of the database. `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE`. These define what can exist.

**DML** (Data Manipulation Language) — statements that work with *data inside* existing structures. `INSERT`, `UPDATE`, `DELETE`, `SELECT`. These operate on rows within already-defined tables.

The practical tension: DDL operations are heavier, sometimes require elevated permissions, and can fail in ways DML doesn't. More importantly, they're harder to undo and harder to query — you can't easily ask "show me all tag types" if each tag type *is* a table, because tables aren't rows.

In SurrealDB specifically, `DEFINE TABLE author TYPE RELATION` would make the database structurally aware of `author` as a relation type — which is clean and enables efficient graph queries. But every time a user creates a new tag type, you're altering the schema, not inserting a record.

The alternative — one `edges` table with a `type: "author"` field — keeps everything as DML. Tag types are just string values on records. Queryable, listable, deletable like any other data. Less efficient for graph traversal, but the schema never changes after initial setup.

The reason this matters for your model specifically: if tag types are navigable entities (which your model implies — you should be able to click "author" and see all authors), they need to be *rows*, not *tables*. A table isn't something you can pin, annotate, or navigate to. A row is.

# Model

In SurrealDB, they can't — tables are schema, not data. You can't store a custom field on the `author` table definition, attach edges to it, or query it as a node. `INFO FOR DB` returns table metadata, but that's not a record you can navigate to or annotate.

So if a user wants to click "author" and arrive somewhere — see all authors, add a note, pin it — `author` needs to exist as a **record**, not just as a table name.

That's the constraint. The question it opens: do you need both? A record representing the concept of "author" as a navigable entity, and a separate `author` relation table for edge storage? That's two representations of the same concept kept in sync.

Or: drop named relation tables entirely. One generic `edges` table, records carry a `type` field. Tag types are just records in `objects`. You lose SurrealDB's native `->` graph traversal syntax but gain a single representation per concept.

The tension is **SurrealDB idiom vs. model simplicity**. Which matters more to you?

# Human

What are the implications for both options

# Model

**Named relation tables per type** (`author`, `genre`, `contains`, each a SurrealDB RELATION table)

- Native SurrealDB graph traversal: `SELECT ->author->objects FROM book:1` — clean, fast, idiomatic
- LIVE SELECT per table is precise
- Creating a user-defined tag type requires DDL at runtime — schema changes, not data changes
- Edge types aren't queryable as data: "list all tag types" requires schema introspection, not a SELECT
- Renaming or deleting an edge type means DDL, not DELETE
- Number of tables grows unboundedly with user-defined types

**Single generic edge table** (`edges` with `in`, `out`, `type` fields)

- Schema fixed after initial setup — all mutations are DML
- "List all edge types" is just `SELECT DISTINCT type FROM edges` — tag types are data
- Loses SurrealDB's `->` traversal syntax; graph queries become standard WHERE clauses
- One large table; needs indexing on `type`, `in`, `out` to stay performant
- Edge types are just strings — the connection between an edge type label and its corresponding Object in `objects` is by convention, not enforced structurally

---

The deeper implication of Option 2: **the edge type label and the tag type Object are two separate things**. Nothing in the database enforces that `edges.type = "author"` corresponds to `objects:author`. That link lives in application code.

Option 1 has the opposite problem: the `author` table and a hypothetical `objects:author` record are also two separate things — same gap, different layer.

Neither option natively unifies the concept. That's the real tension.

---

# Human

How can we unify this?

---

# Model

The gap in both options is the same: edge type as stored data (table name or string) and edge type as navigable Object are two things kept in sync by convention.

One way to close it structurally: make the edge `type` field a **record reference**, not a string.

```
edges record:
  in:   objects:book1
  out:  objects:hemingway
  type: objects:author     ← a record link, not a label string
```

`objects:author` is a real node — navigable, annotatable, with its own edges. The edge type IS the Object, not a name that happens to match one. No dual representation. No convention to maintain.

Creating a tag type = inserting a record into `objects`. Nothing else.

SurrealDB supports filtered graph traversal, so you don't fully lose the `->` syntax:
```
SELECT ->edges[WHERE type = objects:author]->objects FROM objects:book1
```

Slower than named tables, but the model is structurally unified.

The remaining tension worth naming: **system relationships** like `contains` and `excludes` — do they also become Objects in this model? That would mean `objects:contains` is a node you can navigate to, which is either elegant (total uniformity) or strange (what does it mean to arrive at "contains"?).

Does uniformity extend that far, or do system edges stay structural?
